# 写作风格档案

这个文件是文稿的验收标准。写稿前读一遍，写完对照末尾的检查清单过一遍。

## 目标读者

**对 AI 有兴趣，但不是从业者。**

画像：会用 ChatGPT、听说过「大模型」，可能刷到过机器狗视频，但不知道 VLA 是什么、没读过论文、分不清「参数量」和「训练数据量」。

他们点开文章的原因通常是：标题讲了一件具体的事（机器人挤过杂物堆），而不是因为这篇文章解读了某篇论文。

**判断标准**：如果一个句子需要读者先知道另一个术语才能读懂，就改写。

三个栏目共用这套读者设定，但开头钩子不一样：

- **论文 / 项目**：读者点开是因为标题讲了一件具体的事（机器人挤过杂物堆），不是因为「这篇解读了某篇论文」
- **新闻**：读者点开是因为「这跟我有关系」（我用的工具要涨价了、我学的专业要被改写、这家公司要变天）。所以新闻稿前 200 字必须回答「为什么你该看这条」

## 分栏目要求

| | 论文解读 | 项目介绍 | 科技新闻 |
|---|---|---|---|
| 开头 | 一个具体场景，让读者看到画面 | 一个具体用法，或它解决了谁的痛 | 刚发生的那个动作：谁、何时、发布了什么 |
| 素材来源 | 论文 abs 页 + HTML 全文 | 仓库 README / Releases / 代码 | 厂商官方公告 + 一家独立媒体交叉 |
| 配图 | 论文原图 + 自制示意图 | 仓库图 / 界面截图 + 自制示意图 | 官方发布图（注明来源）；无合适图就自制一张时间线或对比图 |
| 必写段 | 局限或不足 | 还缺什么 / 不能做什么 | 还没确认的部分 |
| 结尾信息 | 标题、作者、机构、会议、arXiv 号、项目页 | 仓库地址、star 数、许可证、语言 | 信源列表 + 事件时间 |
| 禁止 | 编造实验数字 | 把半成品说成可用 | 写传闻、做预测、替读者判断股价 |

## 文风

**句子**

- 短句为主，一句话不超过 40 字
- 一段只讲一件事，超过 5 行就拆
- 少用「值得注意的是」「综上所述」「不难发现」这类过渡词
- 可以用「你」「我们」，像跟人聊天，不用「笔者」

**小标题**

口语化，能让读者预判这一节讲什么，最好带一点情绪或反常识。

- 好：「把机器人当成地图上的一个点，是错的」
- 好：「大模型 0.5 秒才想一次，机器人怎么站得稳」
- 差：「方法概述」「实验分析」「结论」

**开头**

从一个具体场景切入，让读者在脑子里看到画面。500 字内必须交代清楚「这件事到底是什么」——论文类是本篇做了一件什么事，项目类是它替谁解决了什么，新闻类是谁在什么时候发布了什么。

禁止用「随着人工智能的快速发展」「近年来，XX 领域取得了长足进步」这类套话开场。

**结尾**

不复述全文，给一个能带走的判断或一句让人记住的话。

## 术语处理（最重要）

**每个术语第一次出现时，就地解释，一句话，用生活里的东西类比。**

不要把这些解释堆到文末做名词表——读者不会翻回去看。

已经验证有效的写法：

| 术语 | 处理方式 |
|---|---|
| 具身智能 | 就是「有身体的 AI」。ChatGPT 只输出文字，具身智能要输出动作 |
| VLA | 视觉 + 语言 + 动作，看着画面、听着人话、直接吐出动作数字 |
| 零样本 | 没在这个环境里练过，第一次见就直接上 |
| 29 个自由度 | 能单独转动的关节有 29 个 |
| 仿真 | 电脑里造的三维假世界，有物理引擎，撞到桌子会真的被挡住 |
| A* | 游戏里点一下地面，角色自己绕开障碍走过去，用的就是这类算法 |
| 动作跟踪器 | 机器人的「小脑」：大脑说手抬到那儿，小脑负责让手稳稳到那儿 |
| 扩散模型 | 先给一团噪声，一步步去噪得到结果。AI 画图是这么干的，这里是生成动作 |
| 消融实验 | 「拆零件」测试：把某部分拿掉，看性能掉多少 |
| SPL | 把成功率和路径长度绑在一起算，绕得越远分数越低 |
| 大模型 / 参数量 | 参数量就是模型的「脑细胞」数量，越多越贵也越聪明，但到某个数之后收益开始变慢 |
| token | 模型处理文字的最小单位。一个汉字大约一到两个 token，一段话就是几百个 |
| 上下文窗口 | 模型一次能同时「记住」多少字。窗口 20 万，等于能一口气看完一本中篇小说 |
| 多模态 | 能同时看图和读字。不是两种模型拼接，而是一个模型两种输入 |
| MoE（混合专家） | 一个大团队里有很多小组，每句话只叫最对口的几个小组来答，其余不参与。看起来人多，实际每次只动用一小部分，所以又快又省 |
| 推理模型 | 先想再答。普通模型脱口而出，它会先在草稿纸上算一遍，所以慢但更准 |
| RLHF | 人给回答打分，模型照着高分方向调。相当于有人一直在旁边说「这个好、那个不行」 |
| 蒸馏 | 让小学徒照着老师的答案练，而不是自己从零摸索。学得快，但老师的天花板就是它的天花板 |
| 量化 | 把高精度数字换成低精度，模型变小变快，代价是偶尔「变笨」一点。像把无损音乐压成 MP3 |
| benchmark / 榜单 | 统一的考卷。分数高不代表真会干活，可能只是这套题刷得多 |
| AGI | 通吃型 AI：一套本事能干所有活。现在没人做到，说「已经实现」的一律当营销 |

**允许直接用的词**：机器人、摄像头、服务器、开源、论文、模型、成功率、碰撞。

**必须解释的词**：所有英文缩写、所有带「度/场/空间/流形」的专业名词、所有算法名。

实在绕不过去的术语，用「说人话就是……」「换句话说……」接一句白话。

## 数字处理

**每个关键数字后面要告诉读者这个数意味着什么。**

反面：「成功率 43.75%」——读者会想「才四成，这模型不行啊」。
正面：「这类任务四成左右就已经是当前最强水平了」——先给坐标系，再给数字。

数字必须来自论文原文。没写的地方就说「论文未提及」，不推测、不估算、不用「大约」。

## 图片

**论文类**

- **论文原图**：从 arXiv HTML 版直接下载原始文件，不用截图，不用 AI 生成冒充
- **自制示意图**：用 `make_diagram.py` 生成，每篇至少 1 张，用来解释机制而不是装饰
- 每张图下面写清是什么，论文原图要标注「论文原图」

**项目类**

- 优先用仓库自带的图（README 截图、架构图、演示 GIF 的一帧），注明出自仓库
- 必须有至少 1 张自制示意图，讲清「它怎么工作」或「它和同类差在哪」

**新闻类**

- 只用官方发布图、官方截图、论文/公告原文里的图，并在图注写明出处与日期
- **不用媒体转载图**（版权与失真风险），找不到合适图就自己做：时间线、参数对比表、事件关系图
- 新闻类同样至少 1 张自制图——一张时间线往往比三段文字更省读者力气

**通用**

- 长文（3000 字以上）图片间隔不超过 600 字，读者需要喘气的地方

## 必须写的一段

**论文类：局限或不足。** 至少 200 字，要具体，不能写成「未来可期」的客套话。好的局限：没开源、只用纯视觉没讨论逆光玻璃、SPL 偏低偏保守、仿真场景比真实仓库干净。

**项目类：还缺什么。** 从 README 的 status / roadmap / TODO 里找，写清哪一步没做完、什么场景还不能用。

**新闻类：还没确认的部分。** 列出这条消息里哪些是厂商自己说的、哪些没有第三方验证、哪些细节官方没公布。这一段的作用是给读者一个判断尺子，不是免责声明。

## 检查清单

交稿前逐条过：

- [ ] 开头 3 行内有画面感，没有「随着……的发展」
- [ ] 每个英文缩写第一次出现都解释了
- [ ] 没有一句话超过 40 字
- [ ] 每个关键数字都给了参照系
- [ ] 至少有一处指出这项工作的局限（新闻类为「还没确认的部分」）
- [ ] 自制示意图至少 1 张，且是用来讲机制的
- [ ] 小标题能让人预判内容，不是「方法」「结果」
- [ ] 结尾没有复述全文
- [ ] 通读一遍，没有需要读者往回翻才能懂的句子

新闻类另加四条：

- [ ] 两个以上独立信源，单一来源的说法已标明「厂商称」
- [ ] 每个数字都能追到一手出处，追不到的写「官方未公布」
- [ ] 全文没有预测性判断（会不会涨、会不会取代谁）
- [ ] 说明了这件事「为什么现在发生」，不只是「发生了什么」
