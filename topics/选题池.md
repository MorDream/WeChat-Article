## 经验沉淀

**标题**：带具体动作或数字的比抽象概念好。"穿过一堆杂物"胜过"全身视觉语言导航"。

**结构**：场景开头 → 旧方法的局限 → 这篇怎么改的 → 数据和训练怎么来 → 结果 → 反直觉发现 → 局限 → 收尾。这个骨架读者反馈最好。

**配图**：论文原图负责"可信"，自制示意图负责"看懂"。一张自制图讲清一个机制，别塞三个。

**数字**：所有数字必须有出处。不确定就写"论文未提及"，不要圆。

**长度**：2500 字左右最舒服，超过 3500 字完读率明显下降。

**篇幅硬限制**：微信 `draft/add` 的 content 字段上限 2 万字符，而每个 `<p>` 带 112 字符的行内样式。2600 汉字配 5 张图大约 1.85 万字符，已接近天花板；再长要拆篇，或把相邻短段合并（用单换行 `<br>` 代替空行分段）。

**栏目**：论文 / 项目两类隔期交替。2026-11-02 起，论文（TANGO）→ 项目（StarVLA）→ 论文（Rho）→ 项目（RPent）→ 论文（Ψ₀）→ 项目（Microduck）→ 论文（ABot-M0）→ 项目（Jumper）→ 论文（VT-WM）。下一篇回到项目类，`待写` 已空，需从备选池提一条或自选。

**预印本要标清楚**：VT-WM 只有 arXiv 版 + OpenReview 投稿记录，项目页与论文都没写录用会议。正文用「状态：预印本」如实交代，别为了贴「顶会论文」栏目硬安一个会议。

**相对涨幅 vs 百分点**：论文爱写 "up to 35% higher"，实际是 69%→93% 的相对涨幅，绝对差 24 个百分点。这类地方必须拆开讲，否则读者会算出 104%。

**项目稿的局限好写**：成熟仓库基本都会在 PROJECT_GUIDE / README 的 status 段里自陈"哪一步还没做完"，直接引用比论文的局限段省事，也更容易写出信任感。
